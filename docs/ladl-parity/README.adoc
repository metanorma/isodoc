= Legacy xref and numbering parity catalogue (F-LADL)

This catalogue maps the legacy xref and numbering methods to the MN112 profile constructs and the LADL engine features at the initial implementation baseline.

IMPORTANT: This is a source-grounded mapping. It is not evidence of runtime parity. No legacy code, engine code or comparison was run to produce it, and it contains no parity percentage or golden result.

== Files

[cols="1,3"]
|===
|File |Content

|`behaviors.csv` |One row per behavior, with layer, status, method IDs, primary citation, MN112 construct, engine feature and gap IDs.
|`methods-common.csv` |The 179 common `isodoc` methods, each assigned to one behavior.
|`methods-flavors.csv` |The 297 flavor and Standoc methods, each assigned to one behavior.
|`PROFILE-GAPS.adoc` |Gap definitions, source anomalies and owner questions.
|===

The behavior rows provide primary source citations. The method tables provide the corresponding repository, path and line.

These counts classify source methods. They must not be read as a percentage of parity.

== Layers and dispatch

The `common` layer is the `isodoc` base. The `flavor-override` layer holds flavor methods. The `excluded` layer holds non-label helpers, DOCX renderers, citation rendering, validation rules and Standoc semantic cleanup.

The `dispatch` column has three values:

* `base` is a method in `isodoc`.
* `same` is a flavor method whose name also exists in the indexed `isodoc` methods.
* `new` is a flavor method with no same-named indexed `isodoc` method.

`same` is a name match. It does not prove which parent the method overrides, because the inventory does not record superclasses, mixins or constants (gap G22). Some flavors override ISO behavior instead of `isodoc` behavior, and `super` calls in the method bodies are the only inheritance evidence available.

Legacy `:arabic` means Western digits. It maps to `DecimalNumericSequence`. The engine's `ArabicNumericSequence` produces Arabic-Indic digits and is a different behavior.

Direction is available in the engine through template and sequence fields. The legacy xref methods have no matching per-label direction field, so direction needs its own comparison evidence.

== Source scope

The classifications describe the initial engine implementation. Later engine repairs need separate verification and gap disposition updates.

The inventory covers 35 repository clones, 49 files and 476 methods.

* 18 repositories contribute methods.
* 6 repositories (CC, CSA, CSD, GB, Generic, VSD) have an xref file with no method definitions.
* 8 repositories have a valid head and no matching xref file.
* 3 repositories (EN, ICC, MLIT) are empty, with an invalid `HEAD` and no files. No behavior is inferred for them.

CSD and CC are at the same commit, consistent with CSD redirecting to CC. Heads are pinned local provenance and are not a claim about the latest remote state.

== Normalization envelope for the ISO legacy and native comparison

The comparison may normalize only the differences listed here. Each normalization must be applied to both sides and must be reported with a count.

[cols="2,3"]
|===
|May normalize |Rule

|Generated footer timestamp |Mask only the known native-harness timestamp field. The S-ISO delivery card tracks retiring this nondeterminism. Authored date content stays compared.
|Random generated IDs |Rename UUID-form generated IDs to first-seen tokens on each side, and rewrite references with the same mapping. Link topology stays compared.
|XML serialization |Canonicalize attribute order, namespace declaration placement and insignificant inter-element whitespace.
|===

The comparison must not normalize any of these:

* label text, numbers, separators, delimiters, case or language
* element names and label field values
* link targets or the element a link resolves to
* counter order or reset behavior
* authored content, including authored dates and authored IDs
* `semx`, `fmt-*` or direction markup, unless an owner approves a named exception

A difference outside the envelope is reported as a difference. If an owner accepts one, record it by gap or anomaly ID with the affected element, instead of widening the normalizer.
